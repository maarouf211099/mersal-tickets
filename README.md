# مرسال — نظام التذاكر (الإصدار الثاني)

نظام تذاكر داخلي يتيح لفرق الإدخال تسجيل بيانات الحالة وتحويلها إلى فريق الاستقبال المختص، مع فصل تام بين أعمال الفرق، ومهل إنجاز (SLA)، ومسار طبي يمر بطبيب الخط الساخن ثم الأبحاث ثم طبيب المتابعة.

📘 **دليل الاستخدام المصوَّر:** [`docs/GUIDE.md`](docs/GUIDE.md)، ويشرح النظام من التسجيل والصلاحيات حتى الإغلاق.

> **تنبيه مهم:** اقرأ قسم [أسباب تعطّل الأنظمة الأخرى مع النسخة القديمة](#أسباب-تعطّل-الأنظمة-الأخرى-مع-النسخة-القديمة)، ففيه مشكلة أمنية تجب معالجتها على السيرفر.

---

## ملخص النظام

| نوع الحالة | مهلة الإنجاز |
|---|---|
| 🚨 طوارئ | 30 دقيقة |
| 🆕 حالة جديدة | 48 ساعة |
| 📋 متابعة | 72 ساعة |

- **مصادر الحالات:** مركز الاتصال، ووسائل التواصل الاجتماعي، والاستقبال، والعيادات.
- **فرق الاستقبال:** فريق الإسكندرية، وخط طوارئ مرسال، والتسجيل والاتصال الخارجي.
- **طبيب الخط الساخن:** لا يظهر خيارًا للتحويل إلا لخط طوارئ مرسال.
- **بيانات التذكرة:** الاسم، ورقمان للهاتف، وكود الحالة، وصلة القرابة، والجنسية، والرقم القومي للمصري أو رقم المفوضية لغيره، والمرفقات.
- **الحالة:** قيد التنفيذ أو مغلقة. ولا يعيد فتح التذكرة إلا المدير أو من مُنح الصلاحية.
- **داخل التذكرة:** تحديثات، وملاحظات، وإشارة إلى الزملاء (@)، وسجل كامل لكل تحويل وتعديل.
- **موديول الموافقات الطبية** منقول من النسخة السابقة كما هو.

## التشغيل على جهاز التطوير

المتطلبات: Node.js 22، وPostgreSQL 14 أو أحدث.

```bash
# 1. قاعدة بيانات خاصة بالنظام (مرة واحدة)
psql -U postgres -c "CREATE DATABASE mersal_tickets;"

# 2. الإعدادات
cp .env.example .env        # عدّل DATABASE_URL وAUTH_SECRET وDEFAULT_ADMIN_PASSWORD

# 3. التثبيت وإنشاء الجداول
npm install
npm run db:migrate          # prisma migrate deploy — آمن ولا يحذف أي بيانات

# 4. التشغيل
npm run dev                 # http://localhost:3005
```

سجّل الدخول باسم المستخدم `admin` وكلمة المرور المحددة في `DEFAULT_ADMIN_PASSWORD`. وإذا تُرك هذا المتغير فارغًا، تُولَّد كلمة مرور عشوائية وتُطبع في السجل عند أول تشغيل.

عند تعديل `prisma/schema.prisma` نفّذ `npm run db:migrate:dev -- --name وصف_التعديل`، ثم ارفع مجلد الـ migration الناتج مع الكود.

## النشر على السيرفر عبر GitHub Actions (Self-hosted Runner)

مع كل دفع (push) إلى الفرع `main`:
1. يتحقق CI على GitHub من الـ migrations وأنواع TypeScript والاختبارات والبناء.
2. إذا نجح كل ذلك، ينفّذ الـ Runner المثبت على السيرفر سكربت النشر `scripts/deploy.mjs`، فيطبّق الـ migrations، ثم يبني النظام، ثم ينشئ إصدارًا جديدًا، ثم يعيد تشغيل `mersal-tickets` في pm2، ثم يفحص سلامة التشغيل.
3. إذا فشل الفحص، يعود السكربت تلقائيًا إلى الإصدار السابق.

### إعداد السيرفر (مرة واحدة)

1. **اجعل المستودع خاصًا (Private)**، فالـ Runner ينفّذ الكود على السيرفر. علمًا بأن النشر لا يحدث إلا من الفرع `main`.
2. ثبّت Node.js 22 وPostgreSQL، ثم:
   ```bash
   npm install -g pm2
   ```
   - على Linux: نفّذ `pm2 startup` ثم الأمر الذي يظهر لك، ليعمل النظام تلقائيًا مع تشغيل الجهاز.
   - على Windows: نفّذ `npm install -g pm2-windows-startup && pm2-startup install`.
3. أنشئ قاعدة البيانات: `CREATE DATABASE mersal_tickets;`
4. أنشئ مجلد النشر، مثل `C:\mersal-tickets` أو `/opt/mersal-tickets`، وضع فيه ملف `.env` بعد نسخه من `.env.example` وتعديله. **لا يُرفع هذا الملف إلى GitHub أبدًا.**
5. سجّل الـ Runner من GitHub: Settings ← Actions ← Runners ← **New self-hosted runner**، واتبع الخطوات، وأضف الوسم (label) التالي: `mersal-tickets`.
   شغّله خدمةً (service) **بالمستخدم نفسه الذي سيشغّل pm2**.
6. من GitHub: Settings ← Secrets and variables ← Actions ← **Variables**، أضف `DEPLOY_DIR` وقيمته مسار مجلد النشر.
7. ادفع إلى `main`، أو من Actions اختر CI & Deploy ثم Run workflow.

أوامر مفيدة على السيرفر:
```bash
pm2 status                 # الحالة
pm2 logs mersal-tickets    # السجل
pm2 restart mersal-tickets # إعادة تشغيل هذا النظام وحده
```

تُحفظ المرفقات في `DEPLOY_DIR/uploads`، فأدرجها في النسخ الاحتياطي مع قاعدة البيانات.

## أسباب تعطّل الأنظمة الأخرى مع النسخة القديمة

1. **🔴 السيرفر مخترق على الأرجح، وعليه برنامج تعدين عملات مشفرة.**
   كانت بين الملفات المرسلة ملفات مخفية باسم `let` و`let;chmod`، وهي برنامج Linux مضغوط بـ UPX تتضمن نصوصه أسماء مثل `xmrig` و`nanopool` و`c3pool` و`kinsing`. هذا النمط معروف لبرامج تستهلك المعالج بالكامل **وتُنهي العمليات الأخرى على الجهاز**، وهو وحده كافٍ لتعطيل كل الأنظمة.
   كانت النسخة القديمة مبنية على `next 15.0.3` و`react 19 RC`، وفيهما ثغرة معروفة (CVE-2025-55182) تسمح لأي شخص على الإنترنت بتنفيذ أوامر على السيرفر. واسم الملف `let;chmod` يوحي بأمر نُفِّذ بهذه الطريقة.

   **المطلوب على السيرفر الذي كانت النسخة القديمة تعمل عليه:**
   - أوقف النسخة القديمة وافصلها عن الإنترنت.
   - ابحث عن العمليات الغريبة التي تستهلك المعالج (`top` على Linux، أو مدير المهام على Windows)، وعن الملفات المريبة في `/tmp`، وراجع `crontab -l` و`~/.ssh/authorized_keys`، وابحث عن الأسماء: `let` و`p.sh` و`alive.sh` و`health.sh`.
   - الأسلم إعادة تثبيت السيرفر، وتغيير **جميع** كلمات المرور والمفاتيح التي كانت عليه: كلمة مرور Postgres، و`AUTH_SECRET`، وأي رموز في ملفات `.env` الخاصة بالأنظمة الأخرى.
   - تعتمد هذه النسخة على `next 15.5.28` و`react 19.2.9`، وكلاهما يتضمن إصلاح هذه الثغرة.
2. **كان `start.bat` ينفّذ `taskkill /F /IM node.exe`**، فيُنهي **جميع** برامج Node على الجهاز، ويُسقط أي نظام آخر يعمل بها. أما هذه النسخة فتعيد تشغيل عملية pm2 المسماة `mersal-tickets` وحدها.
3. **كان `prisma db push --accept-data-loss` يُنفَّذ مع كل تشغيل**، وإذا أشار `DATABASE_URL` إلى قاعدة بيانات فيها جداول لنظام آخر حذفها. أما هذه النسخة فتعتمد على الـ migrations فقط، وجميع جداولها داخل مخطط (schema) مستقل اسمه `tickets`.
4. **ملفات تعريف الارتباط (الكوكيز):** لا يفرّق المتصفح بين المنافذ (البورتات)، فإذا استخدم نظامان على `localhost` الاسم نفسه لكوكي الدخول، أخرج كلٌّ منهما المستخدمَ من الآخر. يستخدم هذا النظام اسمًا خاصًا به: `mersal_tickets_session`.
5. **كلمة مرور Postgres** في ملف `.env` القديم تتضمن الرمز `@` دون ترميز، وقد تقرأ بعض الأدوات `DATABASE_URL` قراءة خاطئة بسببه. الأسلم كتابته `%40` (انظر `.env.example`)، ويجب على أي حال تغيير كلمة المرور بسبب البند الأول.
6. كان الأرشيف المرسل ناقصًا: فالملفات `middleware.ts` و`sse.ts` و`auto-refresh.tsx` وصلت مقطوعة.
